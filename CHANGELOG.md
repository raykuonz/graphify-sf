## [Unreleased]

### Fixed
- **`deduplicate_by_label` no longer drops nodes whose label has no ASCII letters or digits** (for example Japanese Flow element labels) when any other pair of nodes was merged.
- **A commented-out or quoted `setEndpoint(...)` no longer creates an EXTRACTED callout edge.** The Apex callout
  scan read the raw source, so `// req.setEndpoint('callout:Old_NC');`, a block comment, or the same text inside
  a string literal produced a `makes_callout` edge to `Old_NC`. The call must now be real code.
- **`export graphml` works on real graphs.** It raised `TypeError: GraphML does not support type NoneType` because
  every node has `source_location: None`. The export now drops `None` attributes, writes lists and dicts as JSON
  text, and leaves out graph-level metadata.
- **The git merge driver no longer lets the base win or resurrects deleted nodes.** It unioned the base, ours and
  theirs, so a node deleted on one branch came back and the base's attributes won. It now does a real 3-way merge:
  kept when both branches have a node or edge or when one branch added it, deleted when the base had it and either
  branch dropped it (modified-vs-deleted resolves to deleted; `graph.json` is regenerated by the next build), and
  attributes merge per attribute with ours winning conflicts and the base never winning. Edges are matched on their
  logical identity — every field except the volatile ones (`key`, `source_file`, line-number `source_location`, the
  derived `confidence_score`, the constant `weight`, `site_count`) — so a moved line or a recomputed score does not
  make an edge look new and a one-sided deletion sticks; `dml` create and update stay separate edges, and an
  attribute a newer version adds can only split edges, never merge distinct ones. Edges whose endpoint was deleted are
  dropped, so a deleted class does not come back as a stub.
- **A malformed `graph.json` can no longer be merged as an empty graph.** `merge-graphs` aborts before writing
  anything if any named input is unreadable or lacks the `nodes`/`links` arrays, and the merge driver exits
  non-zero (leaving `ours` untouched, so git reports a conflict) if `ours`, `theirs` or a non-empty base is
  malformed. A missing or zero-byte base means "no common ancestor" and gives a plain union.

### Added
- **A coverage ledger in `graph.json`.** A full run now writes a top-level `graphify_sf` block:
  `{"version", "analysis": {<analyzer>: {"status", "eligible", "analyzed", "failed", "sites", "unresolved"}}, "capabilities": [...]}`.
  `capabilities` is derived: the analyzers whose status is `complete`. A graph without the block was never
  analysed, so a consumer can tell "no edges because there is nothing there" from "no edges because nobody
  looked". Counts come from a per-file outcome record, so a file whose extractor raised or whose worker was
  lost counts as failed (`analyzed + failed == eligible` always holds); `complete` means no file failed, `partial`
  some, `failed` all, and zero eligible files is `complete`. Only a full pipeline run (including `--update`, hooks and
  watch rebuilds) writes counters. `cluster-only` and `export json` carry the block through untouched and never
  create or upgrade one; `merge-graphs` and the merge driver write a status-only meet (`"scope": "merged"`, worst
  status per analyzer, an input without a block counts as `not_run`, no counters). `graphify-sf stats` and the
  MCP `graph_stats` tool show it (the MCP fields are `null` when a graph has no block). "Complete" is relative to what
  graphify-sf scanned: files skipped by `.gitignore` / `.forceignore` and bundle or document extraction are not part of an
  analyzer. Only the top-level block counts; a nested `graph.graphify_sf` is ignored and never promoted. Both callout analyzers (`callout-edges.apex`, `callout-edges.flow-http`) are live, so a clean build advertises both
  capabilities.

- **Apex callout endpoints are resolved statically, with a stated confidence.** `setEndpoint(...)` is evaluated as a
  `+` concatenation of string literals and the file's own `String` constants (`static final`, `final`, or instance).
  The edge is EXTRACTED when the target is proven: the whole expression is constant (`'callout:Acme' + '_ERP'` →
  `Acme_ERP`; `BASE + '/v1'` with `BASE = 'callout:Acme_NC'`), or the known prefix already has a delimiter after the
  credential or host (`'callout:Acme/v1/' + id`). A literal `https://host/...` is now EXTRACTED (it was INFERRED).
  `'callout:Acme' + env` is INFERRED with `inference_reason: "dynamic_suffix"` (`"non_final_static"` when the dynamic
  part is a non-final field), because the suffix could extend the credential name; a partial host such as
  `'https://api' + sub` yields no edge. The receiver is classified: a proven `HttpRequest` keeps those rules, a
  receiver declared as another type is not a callout and is ignored, and an unknown receiver is INFERRED
  (`receiver_unproven`). Sites are grouped per `(target, confidence, test_context, inference_reason)` into one edge
  with `site_count` and the first `source_location`, so production and test calls, or EXTRACTED and INFERRED calls to
  one target, stay separate parallel edges. Sites in `@IsTest` classes or methods and in `testMethod` methods carry
  `test_context: true`. Apex triggers are scanned too. The `callout-edges.apex` ledger entry counts `sites` and
  `unresolved` (sites that did not end in an EXTRACTED edge); a file whose extractor does not report its sites counts
  as failed. When `unresolved > 0`, treat "no callers" findings as candidates. Counts are taken per site by the
  extractor, before cross-file adjustments (a host-id collision later downgrades its edges to INFERRED without
  changing `unresolved`). A name resolves to a constant only if the file declares it exactly once in any form
  (field, property, local, parameter, for-each variable, later declarator); a shadowed or redeclared name is dynamic.
  An argument with a ternary, comparison or assignment (`?`, `:`, `=`, `!`, `<`, `>`, `&`, `|`) is dynamic as a whole.
  `this.a.b.setEndpoint(...)` and `obj.field.setEndpoint(...)` have an unknown receiver; `new Other().setEndpoint(...)`
  is not a callout. A target known only by a prefix (`'callout:Acme' + env`) keeps its INFERRED edge but never gets a
  stub node, because the real credential is probably `Acme_Something`.
- **Flow HTTP callouts are read from `httpCallout` actions only, in both shapes.** `<stringValue>callout:Name/path`
  under an input parameter and `<actionName>callout:{{Name}}` (or `callout:Name`) on the action itself resolve to a
  `makes_callout` edge to the Named Credential, EXTRACTED, with `source_location` set to the action name and
  `site_count` when several actions share a target. A literal `https://host/...` is EXTRACTED too and creates its
  `ExternalEndpoint` node. A `callout:` string inside any other action type (an email body, a chatter post) no longer
  produces an edge. Every `httpCallout` action is a site in the `callout-edges.flow-http` ledger entry; one that
  yields no edge (a merge-field host, a form this version does not read) counts as `unresolved`, so a Flow-only
  consumer can tell "no callers" from "callers we could not read". Modern External Service / Named Credential
  action forms are not guessed.
- **Callout targets that are not in the repo now appear in the graph.** A `makes_callout` (Apex, Flow) or `uses`
  (External Service, External Data Source) edge to a Named Credential whose metadata is not in the project used to be
  dropped when the graph was built, so a class calling `callout:Not_In_Repo` showed no callout at all. The target is
  now a stub node (`stub: true`, no `source_file`, exact `sf_type`, original-case label) and the edge stays
  EXTRACTED. A real node always replaces a stub with the same id, in either order (in a 3-way merge only when both sides added it; a deleted metadata file stays deleted). A stub is never folded into a different node that merely has a similar label.
- **A Flow that calls a literal URL now creates the `ExternalEndpoint` node itself.** Before, the edge survived only
  if some Apex class happened to call the same host; otherwise it was dropped.
- **`ExternalEndpoint` ids that collide are flagged instead of silently conflated.** `make_sf_id` is lossy, so
  `api.example.com` and `api-example.com` share an id. Ids are unchanged, but such a node now carries
  `identity_ambiguous: true` and `hosts: [...]`, and calls to it are INFERRED with
  `inference_reason: "host_id_collision"`; do not read "unreferenced" off an ambiguous node. Adding a second host
  that collides with an existing one can therefore turn an earlier EXTRACTED edge INFERRED.
- **Apex files whose class header the declaration regex misses are no longer invisible.** A `.cls` file whose own
  declaration the header regex cannot parse (typically a dotted `implements Database.Batchable<sObject>`, or a
  header without an access modifier) produced no node and no analysis, and an inner type with an access modifier
  could rename the outer class. The header named after the file is now preferred; when it cannot be parsed, the file
  gets a node named after it (`declaration_unparsed: true`, kind taken from the `class`/`interface`/`enum` keyword)
  and is analysed like any other class. A `.cls` file that declares no Apex type (LaTeX, VB6) still produces
  nothing. Many more real ApexClass nodes can appear (every Batchable); no existing id changes, and ApexClass inbound
  EXTRACTED counts are identical to 0.5.0 on every test fixture. Classes started only through
  `Database.executeBatch(new X())` have no inbound edge, so an orphan list will list them.

### Changed
- A Named Credential name in a callout ends at `/`, `?` or `#`; a merge-field host such as `https://{!Host}/x` is not an endpoint.
- `merge-graphs` now fails on a malformed input where it used to skip it silently.
- The merge driver takes no output-directory lock: git hands it its own temporary `.merge_file_*` files, never the
  live `graph.json`, so there is nothing to serialise against.

## [0.5.0] — 2026-10-28

Housekeeping release: Python 3.10 is dropped, OpenAI's default model changes, and the release pipeline
stops trusting moving inputs. There are no changes to extraction or to the graph.

### Removed
- **Python 3.10.** It reached end of life this month. `graphify-sf` now requires Python 3.11 or newer;
  on 3.10, `pip` keeps resolving **0.4.7** (the last release that supports it). CI tests 3.11–3.14. The
  npm package and the prebuilt binaries are unaffected (the binaries bundle Python 3.12).

### Changed
- **OpenAI default model: `gpt-4.1-mini` → `gpt-6-luna`.** OpenAI shuts `gpt-4.1-mini` down on 2027-01-14
  and names `gpt-6-luna` as its replacement. Price $0.40/$1.60 → $0.10/$0.50 per 1M tokens, but
  `gpt-6-luna` is a reasoning model, so its reasoning tokens are billed as output and the real cost
  depends on the token mix.
  - For `gpt-6*` models the request omits `temperature` and sets `reasoning_effort="low"`. Other models
    (for example `GRAPHIFY_SF_OPENAI_MODEL=gpt-4.1-mini`, which keeps working until its shutdown) are sent
    exactly what they were before.
  - If the API rejects `temperature` or `reasoning_effort` with a 400, the request is retried once
    without them and the rejection is remembered for the rest of the run. This applies to the `openai`
    backend only; the Gemini, Kimi and Ollama backends are unchanged.
  - If a reasoning model spends the whole output budget thinking and returns nothing, the message now
    says so and points at `GRAPHIFY_SF_MAX_OUTPUT_TOKENS`; the chunk is still bisected as before.
  - Cost lines say "at default-model rates" when `GRAPHIFY_SF_OPENAI_MODEL` selects another model.
  - **Not verified against the live API** (no OpenAI key was available): the `temperature` and
    `reasoning_effort` handling and the price come from OpenAI's documentation. If you see a 400 or an
    odd bill, set `GRAPHIFY_SF_OPENAI_MODEL=gpt-4.1-mini` and tell us.

### Security / release pipeline
- **Every GitHub Action is pinned to a commit SHA** (including `pypa/gh-action-pypi-publish`, which was a
  moving branch); uv and npm are pinned to exact versions, and the release jobs do not use caches.
- **The Linux binary's base images are pinned by digest** (`.github/docker/manylinux-*/Dockerfile`, kept
  current by Dependabot). The `dnf upgrade` inside the container is deliberately not pinned: it brings
  the bundled libraries to the latest security errata. The two `dnf` calls now retry on mirror errors.
- **Binary-build dependencies are hash-locked.** PyInstaller, pyelftools and setuptools live in a
  `binary` dependency group in `uv.lock`; every binary build installs a hash-checked export of it
  (`pip --require-hashes --only-binary=:all:`) and then the project with `--no-build-isolation`. The
  documentation extras are no longer installed for the binary (they were excluded from it anyway).
- **Build legs can no longer write to the release.** `release-binaries.yml` is split into `resolve` →
  `build-binaries` (read-only; third-party build code) → `attach-assets` (the only job that writes the
  release; runs no PyPI or npm package code) → `publish-npm` (npm OIDC token, no release write access).
  Published assets are still never replaced, the checksums are computed from the published bytes, and
  the npm job verifies the binaries it packs against them.
- **`publish.yml`:** the PyPI OIDC permission is now only on the publish job, not the build job.
- **Both release workflows refuse a tag that differs from `pyproject.toml`'s version**, so PyPI and npm
  can't be published at different versions; a test also keeps `pyproject.toml`, `uv.lock` and the npm
  package and its five platform pins in step.
- **`workflow_dispatch` has a `dry_run` mode** that builds from the dispatching ref and exercises every
  job without writing to the release or the npm registry (it packs instead of publishing, outside the
  `npm` environment).
- **A manual re-run needs a tag from v0.5.0 on.** Older tags predate the hash-locked build and fail an
  explicit preflight check.
- PR CI now also builds the macOS Intel binary and checks that `uv.lock` is up to date.

### Known issues
- `publish.yml` (PyPI) and `release-binaries.yml` (binaries, npm) both start on `release: published` and
  are independent, so PyPI can ship while the binary build fails. Re-running the failed jobs finishes the
  release. Gating PyPI on the binaries is planned.
- The smoke-test distro images and the runner images (`ubuntu-latest`, `windows-latest`) are still
  referenced by tag.

## [0.4.7] — 2026-10-23

A small release for the git hooks and `graph.json` writes. Two behaviours change; see **Changed**.

### Fixed
- **`graphify-sf hook install` never updated an installed hook.** It stopped at "already installed", so
  none of the hook fixes since 0.4.4 (the 0.4.5 file filter, the 0.4.6 append-only log, and the
  rotation below) reached existing repositories unless you ran `hook uninstall` first. It now replaces
  graphify-sf's own block with the current one and leaves the rest of the hook file alone (including
  `core.hooksPath` and Husky hooks; a symlinked hook is written through the link and keeps its
  mode); anything you edited inside graphify-sf's own block is replaced. It says `updated`, `already up to date`, or, if the block has
  lost its end marker, leaves the file untouched and tells you to remove the section by hand
  (`hook uninstall` now says the same instead of claiming it removed it). **Run `graphify-sf hook install`
  again in each repository after upgrading.**
- **The hook log grew without limit.** `~/.cache/graphify-sf-rebuild.log` is now moved to
  `graphify-sf-rebuild.log.1` once it passes 1 MiB (about 1–2 MiB is kept). The check only reads file
  metadata and can't fail the hook, so it is safe under `set -e`. Two hooks racing can lose one
  rotation's log lines.
- **A killed run left `.graph.json.<pid>.<id>.tmp` files behind.** The next write removes ones that
  are an hour old and match that exact name; other files, symlinks and directories are never touched.
- **A bind-mounted `graph.json` gave a bare error.** (Docker `-v host/graph.json:/out/graph.json`
  can't be replaced by a rename; it failed since 0.4.6.) The error now says why and how to proceed.

### Changed
- **`GRAPHIFY_SF_NONATOMIC_WRITE=1` allows an in-place write for exactly that case** (`EBUSY` or
  `EXDEV`). It is off by default because it is not crash-safe: an interrupted write can leave a
  damaged `graph.json`. The old content is restored if the write fails, and the complete new graph is
  kept beside it as a `.tmp` file (the next write removes it once it is an hour old). Mounting the output directory instead needs no switch. A `graph.json` that can't be
  replaced because it is held open or the directory is read-only (`PermissionError`) still fails and
  leaves the old file untouched.
- `hook install` rewrites graphify-sf's block in hook files that already contain it (see Fixed).

## [0.4.6] — 2026-10-23

A bug-fix release for the output directory, concurrent runs and `graph.json` writes. Four
behaviours change; each is listed under **Changed**.

### Fixed
- **A custom `--out` inside the project was scanned as part of the project.** Only the name
  `graphify-sf-out` was skipped, so with `--out <project>/reports` (or `GRAPHIFY_SF_OUT`) the run's
  own `GRAPH_REPORT.md` and `graph.html` were read back in as documents, and the graph grew on every
  run (6 → 24 → 26 links on a small project). The output directory is now never scanned, whatever it
  is called and however its path is spelled (case, `out/.`). A run that skips one prints
  `not scanning the output directory …`. If `--out` is the project root itself it can't be excluded,
  and a warning says so.
- **Git hooks, the CLI and `watch` could overwrite each other's output.** The post-commit and
  post-checkout hooks both start a background rebuild, and nothing stopped two runs from writing the
  same files with the older tree finishing last. Runs now take turns per output directory: a plain
  or `--update` run, the git hooks, `watch`, `cluster-only`, `export json` and `merge-graphs`. The
  second prints `another run is updating <dir>; waiting…` and continues when the first is done. The
  other `export` formats don't take the lock.
  - It gives up with exit 1 after 15 minutes. Set `GRAPHIFY_SF_LOCK_TIMEOUT` (seconds) to change
    that. Each hook run waits its own turn, so several quick commits mean several rebuilds in a row.
  - `watch` waits as long as it takes, and folds the changes that arrive meanwhile into one rebuild
    instead of queueing one per change. Its first build is skipped if a run that held the lock
    already produced `graph.json`.
  - A run that is killed does not leave the lock behind, and neither do its extraction workers.
  - **Not covered:** Windows (no `flock`) and filesystems that don't support it (some network
    mounts) run unlocked, as before. A warning says so when the filesystem refuses the lock.
- **An interrupted run could leave a truncated `graph.json`.** It is now written to a temporary file
  and renamed into place, so `serve` and other readers see the old file or the new one. If the
  rename keeps failing (on Windows, another program holding the file open), the run exits 1 with a
  clear error and the previous `graph.json` is left untouched. Permission bits and symlinks are
  kept; hardlinks, owner and ACLs are not. A run killed at the wrong moment can leave a hidden
  `.graph.json.*.tmp` file in the output directory.
- **A refused write still produced a report and HTML.** When `graph.json` was not written, the new
  `GRAPH_REPORT.md`, `graph.html`, labels and `manifest.json` were still written next to the old
  graph, and `check-update` then hid the stale graph. `graph.json` is now written first, and the
  report, labels, manifest and HTML are written only after it succeeds. `cluster-only` and
  `merge-graphs` write the graph first too, and `cluster-only`, `merge-graphs` and `export json`
  exit 1 with one error line when the graph can't be written. (Converted `.docx`/`.xlsx` sidecars
  are produced while scanning, so they can exist even when the graph isn't written.)
- **The npm launcher printed a doubled prefix** (`graphify-sf: graphify-sf: sha256 mismatch …`).
- **CHANGELOG link references** stopped at 0.3.5; 0.3.6–0.4.6 are added.

### Changed
- **A plain run that would shrink `graph.json` now exits 1** (it printed a warning and exited 0).
  The old graph is kept and nothing else is written. `--force` still overrides, and `--update`
  never needs it.
- **Document sidecars** (converted `.docx`/`.xlsx`) are written under `<out>/converted` instead of
  always `<project>/graphify-sf-out/converted`. They only move when the output directory isn't
  `<project>/graphify-sf-out`: a custom `--out`, or running from a different directory (the
  default `graphify-sf-out` is relative to where you run the command). A stray
  `graphify-sf-out` folder no longer appears in the project, except when `--out` is the project root.
- **A read-only `graph.json` is replaced** on macOS and Linux (the old in-place write failed on it; on Windows it still fails), while a `graph.json`
  that is a single-file bind mount, or sits in a directory you can't write to, now fails (exit 1).
- **The hook log is appended to** instead of overwritten, so two hooks can't scramble it; it is not
  trimmed. Run `graphify-sf hook uninstall` and `graphify-sf hook install` to get the new hook text.
  The lock needs no reinstall: it lives in the CLI that the hooks call.

## [0.4.5] — 2026-10-23

A bug-fix release. One fix changes behaviour: `--update` now rebuilds the graph instead of merging
into it.

### Fixed
- **`--update` duplicated edges and kept deleted files.** Extraction was never incremental: `--update`
  re-parsed every file and then unioned the result with the previous `graph.json`. Every run added
  another copy of each edge (6 → 12 → 18 links on a small project), and nodes and edges from deleted
  files were never removed. `--update` now builds the graph from this run's extraction alone, so
  repeated runs produce the same graph and deleted files drop out.
  - `--update` may shrink `graph.json` without `--force`, because a smaller graph is the correct
    result after files are deleted or edited. It covers exactly the path it is given, so `--update`
    on a subdirectory replaces the graph with that subdirectory. A file that fails to parse drops out
    until it parses again.
  - `--update` refuses, exits 1 and writes no graph when the old graph holds LLM-derived facts and
    this run merged none (no `--backend`, or the backend was missing or failed completely). The
    hooks and the watcher never pass `--backend`, so without this check they would silently discard
    paid LLM output. `--force` drops the LLM facts anyway. If the backend fails only partly, the LLM
    facts are replaced by what succeeded.
    - LLM output is now tagged `extractor: "llm"`. Graphs from older versions are recognised by the
      relative `source_file` that LLM nodes and edges carry; static extractors record absolute paths.
  - The `watch` command and the hooks installed by `graphify-sf hook install` run `--update`, so they
    follow these rules too. A graph built with `--update` on 0.4.4 or earlier may contain duplicate
    edges; one run on 0.4.5 replaces them. A graph built with `--include-ignored` loses the ignored
    files on the next `--update` that doesn't pass it.
- **`built_at_commit` recorded the wrong repository.** It came from `git rev-parse HEAD` in the
  process's working directory, so running graphify-sf from another checkout (as sf-cockpit does)
  stamped that checkout's commit. It now comes from the analysed project's repository, read before the
  scan starts, and inherited `GIT_DIR`/`GIT_WORK_TREE` variables no longer redirect it. It is omitted
  when the project isn't in a git repository.
  - `cluster-only` and `export json` keep the commit the graph was built from instead of stamping the
    current one.
  - `merge-graphs` and the git merge driver record none, because a merged graph has no single
    source commit.
- **The tree and call-flow HTML exports rendered node text as markup.** Node labels and source paths
  come from project files. `export tree` wrote them into its tooltip with `innerHTML` and embedded the
  data without escaping `</`, so a crafted file name or markdown heading could inject HTML or script
  into the page. The tooltip is now built from text nodes, and every `<` in the embedded data (in
  `graph.html` too) is escaped, so node text can't close the `<script>` element or blank the page with
  `<!--`. `export callflow` now HTML-escapes the Mermaid source and keeps quotes inside labels.
- **The `export tree` page never rendered.** Its script had a syntax error
  (`d3.linkHorizontal(){x: …}`), so the browser rejected the whole script and the page stayed blank.
- **The watcher and the post-commit hook ignored most metadata.** `watch` only reacted to 17 file
  suffixes, so changes to LWC and Aura components, Named Credentials, External Services, Remote Site
  Settings, sharing rules, reports and many other types never triggered a rebuild. It now reacts to:
  - every suffix the detector classifies;
  - files in LWC and Aura bundles;
  - renames away from those;
  - deleted or moved folders.

  It skips the same directories as the detector, plus `.sf`, counted from the watched folder down, so
  a project inside a `build/` or `.claude/worktrees/` folder is still watched. It ignores open/close
  events, which could retrigger rebuilds on some platforms. Reference documents (`.md`, `.pdf`, …)
  still don't trigger a rebuild.

  The post-commit hook likewise skipped commits that changed only LWC, Aura or Visualforce files. To
  get the new hook, run `graphify-sf hook uninstall` and then `graphify-sf hook install`.

### Changed
- `export.to_json()` stamps `built_at_commit` only when it is passed one, and
  `export._git_head()` now takes the project path. Both previously used the process's working
  directory.

### Removed
- `graphify_sf/cache.py`, an extraction cache that nothing called, and `build.build_merge_sf`, which
  only `--update` used and which duplicated edges.

## [0.4.4] — 2026-10-21

A Linux-compatibility release for the npm binaries. The Python package is unchanged apart from its
version.

### Fixed
- **The Linux binaries now run on glibc 2.28 and newer.** Every Linux binary to date (0.3.2–0.4.3,
  x64 and arm64) needed glibc 2.38, so it failed with `GLIBC_2.38 not found` on Debian 12 (bookworm,
  including `node:*-bookworm` Docker images), Ubuntu 22.04, and RHEL/AlmaLinux 9. Reported by the
  sf-cockpit maintainers (sf-cockpit #38).
  - The cause: the launcher only needs GLIBC_2.14/2.17, but PyInstaller bundles `libpython`,
    `libcrypto`, `libreadline` and Python's extension modules from the build machine. That machine was
    the Ubuntu 24.04 runner (glibc 2.39).
  - The Linux binaries are now built inside `manylinux_2_28` (AlmaLinux 8, glibc 2.28), using
    AlmaLinux's security-maintained Python 3.12.
  - Supported: RHEL/AlmaLinux/Rocky 8+, Debian 11+, Ubuntu 20.04+, Amazon Linux 2023. Older glibc
    (Amazon Linux 2, CentOS/RHEL 7) and musl-based distros (Alpine) aren't supported by the binary;
    `pipx install graphify-sf` works there.
  - The binary's bundled runtime libraries now come from EL8 and are maintained by Red Hat: Python
    3.12.15, OpenSSL 1.1.1k (with backported fixes) and expat 2.5.0. The build applies all EL8
    errata first and logs the bundled package versions. The binary does no TLS: the LLM SDKs aren't
    bundled, and OpenSSL is used only for hashing.
  - A smoke run with `OPENSSL_FORCE_FIPS_MODE=1` (as on FIPS-mode hosts) builds a graph
    successfully. This shows the binary works there; it isn't a FIPS-compliance claim.

### CI and maintenance

## [0.4.1] — 2026-07-14

A correctness- and honesty-focused release: closes several MultiDiGraph parallel-edge-drop gaps left
over from the 0.4.0 migration (including two introduced by this release's own new code, caught and
fixed during a multi-round adversarial review before shipping), hardens the Apex extractor against
comment/string false positives, normalizes LLM backend config drift, and fixes ambiguous doc-mention
resolution. Every fix below shipped with a regression test proven to fail on the pre-fix code.

### Fixed — MultiDiGraph parallel-edge drops (serve.py, merge-graphs, and the new bfs_impact tool)
- **MCP tools and the CLI's `path` command now read every parallel edge, not just the first.**
  `serve.py`'s `get_node`, `get_neighbors`, and `shortest_path`, plus `graphify-sf path`, previously
  called the single-edge `edge_data()` helper on the default MultiDiGraph, so a node pair with two
  relations (e.g. `queries` + `dml` to the same object) silently reported only one of them — the same
  class of bug the 0.4.0 MultiDiGraph migration fixed elsewhere, unfixed in the MCP/CLI layer until now.
  All four now use `edge_datas()` and surface every relation. `get_node`/`get_neighbors` may now return
  one entry per relation instead of one per neighbor (each entry still shaped
  `{id, label, sf_type, relation, confidence}`); `shortest_path`'s per-hop `relation`/`confidence`
  becomes a list when a hop has more than one parallel edge (a scalar for the common single-edge case).
  **If you consume these MCP tools, re-check any caller that assumed exactly one entry per neighbor.**
- **`merge-graphs`/`merge-driver` no longer drop parallel edges, on either axis.** The union previously
  went through a plain `nx.Graph()`, collapsing same-direction parallel edges (e.g. `queries` + `dml` on
  one pair) before the multigraph-aware rebuild ever ran; then, after being rewritten to preserve those,
  it dropped edges that shared a relation but differed only in `operation` (e.g. two `dml` edges, one
  `create` one `update`, on the same pair). The union now hashes the full edge identity (minus the
  per-graph `key`/`source_file` fields that legitimately vary across inputs), so every distinct parallel
  edge survives a 2- or 3-way merge while genuinely-identical duplicates (the base/ours/theirs case)
  still coalesce to one.
- **The new `bfs_impact` MCP tool (see Added) now reports every parallel relation to a neighbor.** Its
  first implementation stored one `{relation, confidence}` pair per neighbor id in its BFS accumulator,
  re-introducing — in code this same release added — the exact parallel-edge collapse fixed above for
  the other MCP tools. `relation`/`confidence` are now lists when a neighbor has more than one parallel
  edge (a scalar for the common single-edge case), mirroring `shortest_path`.

### Fixed — Apex extraction honesty (comments, strings, method scoping, generics)
- **Apex class extraction no longer treats commented-out or string-literal code as real.** `insert`/
  `update`/etc. inside `//`, `/* */`, or a string literal previously produced real edges to a nonexistent
  target; comments and string contents are now scrubbed before `extract_apex_class`'s DML, method-call,
  SOQL, `EventBus.publish`, and Custom Metadata/Setting-access extraction.
- **Known gap (disclosed, not fixed this release):** Apex HTTP-callout detection
  (`extract_apex_class`'s endpoint scan) and `extract_apex_trigger`'s call-scanning still read raw,
  unscrubbed source, so commented-out or string-embedded code in those two paths can still produce a
  phantom edge. Pre-existing, not introduced by the fix above; tracked for a future release.
- **Apex `calls` edges no longer leak across method boundaries.** A method's call-edge scan previously
  ran to end-of-file instead of to its own closing brace, so every method accumulated calls that
  actually belonged to methods below it in the same class.
- **Apex `implements` clauses with a generic argument list no longer split incorrectly.**
  `implements Comparator<Account, String>` previously split on the comma inside the generic brackets and
  emitted a bogus edge treating `String` as an interface.
- **Apex DML operand→type resolution is now scoped per method, not per class.** Two methods reusing the
  same local variable name with different declared types (e.g. `Account a` in one method, `Contact a` in
  another) previously collided via `dict.setdefault`, silently misattributing the second method's DML.

### Fixed — LLM backends, doc mentions, MCP robustness, --verbose accounting
- **LLM backend config drift across the 6 supported backends resolved.** OpenAI previously had no
  `max_tokens` entry and fell back to a hardcoded `8192` (half of every sibling backend's `16384`);
  Gemini silently ignored the documented `GRAPHIFY_SF_MAX_OUTPUT_TOKENS` env override; `temperature` was
  never passed to Claude's SDK call and was hardcoded (ignoring config) for Bedrock. All 6 backends now
  resolve `max_tokens`/`temperature` through the same codepath. Kimi's thinking-disable and Ollama's
  context-sizing quirks moved from inline branches to a data-driven per-backend hook with no behavior
  change (proven by regression test). **The `openai` backend's effective `max_tokens` changes from 8192
  to 16384** — this changes output size/cost for existing `--backend openai` users; not a silent change.
- **Doc/PDF cross-reference mentions no longer resolve to an arbitrary match when ambiguous.** When a
  mention's label matched multiple graph nodes, the resolver previously picked the first one arbitrarily
  (e.g. a `DocumentSection` heading could win over the real `CustomObject` it was named after). It now
  prefers non-document candidates, and falls back to emitting all remaining candidates at a reduced
  `INFERRED` confidence score when the ambiguity is real. A small denylist now filters common English
  words that happen to be PascalCase-shaped (suffixed names like `Account__c` always bypass it), and a
  mention inside a fenced or inline code span now gets a higher confidence score than one in bare prose.
- **MCP tool int arguments (`bfs_impact`'s `max_depth`/`limit` and others) no longer raise on
  non-numeric input.** A caller-supplied non-numeric value previously raised an uncaught `ValueError`;
  a new `_get_int` helper now degrades to the tool's default and clamps out-of-range values.
- **`--verbose` node accounting no longer mislabels retained nodes as stubs on `--update`.** Incremental
  mode merges with the entire prior `graph.json`, so a node carried over unchanged from a file no longer
  on disk was counted as a build-injected stub; the stub term now reports `n/a (incremental merge)` on
  the incremental path, matching the existing `n_pruned_edges` guard.

### Added
- **`bfs_impact` MCP tool** — a depth-bounded, direction-aware (`forward`/`reverse`/`both`) blast-radius
  traversal, EXTRACTED-edges-only by default (`include_inferred` opt-in), with `relation_filter`,
  `limit`/`truncated` reporting, and a `by_type` breakdown. Closes the gap between graphify-sf's own
  1-hop-only `get_neighbors`/`get_node` tools and the multi-hop impact analysis downstream consumers had
  to reimplement on top of raw `graph.json`.
- **`--verbose`/`-v` node-drop accounting** on build/update — prints
  `N extracted → M deduped-by-label (K merged) → +S stub → F final nodes (P dangling edge(s) pruned)` so
  the extract→dedup→build node-count pipeline is no longer opaque.

### Verification
- 503 tests (up from 451 at 0.4.0), `ruff check`/`ruff format --check` clean, zero new runtime
  dependencies. Every fix above was independently reproduced against a pre-fix checkout before and after
  the change, not just asserted by a passing test suite.

## [0.4.0]

### ⚠️ BREAKING CONTRACT CHANGE — graph.json is now a MultiDiGraph

**graph.json now declares `"multigraph": true`.** Every entry in `links` carries
a `"key"` integer. A single node-pair **may appear multiple times** in `links`,
each entry with a distinct `key` and its own `relation`. Downstream consumers that
assume "one edge per source→target pair" will silently read only the **first**
relation and drop the rest — a correctness regression, not a crash. **Every
consumer must switch from `find(…)` to `filter(…)` when reading `links`.**

This fulfils the planned 0.4.0 MultiGraph work noted in the 0.3.6 CHANGELOG.

#### Why the change is needed
`build_from_json` previously built an undirected simple `nx.Graph()` where a
node-pair holds ONE edge. Same-direction parallel relations — e.g. an Apex class
that BOTH `queries` AND `dml`-writes the same object — collapsed silently: the
second `add_edge` overwrote the first. On a real org this erases ~149
`{queries,dml}` pairs. The loss was invisible in graph.json (0 multi-relation
pairs ever survived).

#### What changes
- `build_from_json` / `build` / `build_merge_sf` now default to
  `multigraph=True`, constructing a `nx.MultiDiGraph` that stores **all**
  parallel directed edges without collision.
- The old `_RELATION_PRIORITY` collision path (kept for `multigraph=False`) is
  bypassed entirely for the default MultiDiGraph path.
- `node_link_data(G, edges="links")` serialises the MultiDiGraph natively; each
  link gains a `"key"` field. `node_link_graph` reconstructs the MultiDiGraph
  automatically when it sees `"multigraph": true`.
- Consumer query sites (`--explain --filter-relation`, Obsidian export, analysis)
  now iterate `edge_datas(G, u, v)` so all parallel relations are found, not just
  the first.

### Added (Epic A–F coverage breadth)
- Integration & external dependencies (A1–A8): HTTP callouts, Flow callouts,
  RemoteSiteSetting, ExternalDataSource/ExternalObject, PlatformEvent/CDC,
  Custom Metadata/Settings config reads, AuthProvider/CSP/CORS, Workflow outbound
  messages.
- Security & sharing (B1–B5): Org-Wide Defaults, SharingRules/SharingSets,
  PermSetGroup membership, Profile/PermSet userPermissions + tab/app visibility,
  RestrictionRule + Duplicate/MatchingRule.
- Automation completeness (C1–C4): WorkflowFieldUpdate/Task, ProcessBuilder
  distinction, Flow trigger completeness, ValidationRule standard field refs.
- UI layer → backend linkage (D1–D3): LWC schema/label/resource imports,
  Aura/VF controller linkage, FlexiPage Aura embeds + StaticResource/QuickAction/
  CustomTab-App edges.
- Data model completeness (E1–E3): FieldSet/GlobalValueSet, CompactLayout/
  ListView/RecordType inner refs, polymorphic lookups.
- Reporting & packaging (F1–F2): Report/Dashboard/ReportType extraction,
  Package/InstalledPackage nodes + namespace tagging.

### Fixed (cleanups)
- `EventBus` platform type no longer becomes a phantom `ApexClass` node when
  `EventBus.publish(...)` appears in Apex. `eventbus` is now in the keyword
  exclusion set so it is never treated as a user-defined class reference.
- `CustomField --uses--> GlobalValueSet` edge is now emitted exactly once per
  field even when the underlying XML has multiple `<valueSet>` elements.
- `ApexTrigger --subscribes--> PlatformEvent` edge is now emitted (in addition
  to the existing `triggers` edge) whenever a trigger fires on a `__e` object.

  proxy-restricted environments.
- npm-side regression test suite (`npm/test/`, Node's built-in `node:test`, zero dependencies) covering the
  non-fatal postinstall behaviour and `GRAPHIFY_BIN` resolution precedence.

## [0.3.7] — 2026-06-14

### Fixed
- **macOS: parallel extraction no longer crashes the worker pool and silently truncates the graph.**
  The PyInstaller-frozen binary had no `multiprocessing.freeze_support()` call, so on macOS (and Windows),
  where the multiprocessing start method is **spawn**, each pool worker re-executed the binary with Python's
  internal bootstrap args (`-B --multiprocessing-fork <fd>`). The CLI argument parser intercepted those args
  first, rejected them (`error: unknown command '-B'`), and every worker died — leaving only the lightweight
  sequentially-extracted bundles (LWC/Aura/Document) and producing a severely truncated graph (e.g. 572
  nodes instead of ~9700, with **zero** CustomObject/CustomField/Flow). Linux was unaffected because it uses
  the `fork` start method (no re-exec). `freeze_support()` now runs first in the entry point, so spawn workers
  bootstrap correctly. Verified by building the frozen binary and running it under a forced `spawn` start
  method: full graph restored (9383 nodes, 658 objects, 3239 fields, 166 flows).
- **A failed worker pool no longer produces a silently-incomplete graph that exits 0.** Previously a
  `BrokenProcessPool` was caught per-future and swallowed, so the run continued with only partial results and
  still exited successfully. Any pool-level failure now aborts parallel mode and re-runs the **full**
  extraction sequentially, emitting a loud `WARNING: parallel worker pool failed — falling back to sequential`
  so the produced graph is always complete (just slower) and the degradation is visible.

### Added
- `GRAPHIFY_SF_MP_START` environment variable to override the multiprocessing start method
  (e.g. `GRAPHIFY_SF_MP_START=spawn`/`fork`) — primarily an escape hatch and a way to exercise the spawn
  re-exec path on Linux. Unset uses the platform default.

## [0.3.6] — 2026-06-14

### Added
- **`.gitignore` / `.forceignore` are now honored by default** to cut graph noise. Files matched by the
  project's `.gitignore` or `.forceignore` (deprecated metadata, queues, `__tests__`, jsconfig/eslint/ts
  scaffolding, build output, etc.) are skipped during the scan instead of becoming phantom nodes. Patterns
  are parsed with `pathspec` gitignore semantics — negation (`!keep`), anchored (`/foo`), directory
  (`foo/`), and `**` globs all behave the same as git and the `sf` CLI (the previous `.graphifysfignore`
  used `fnmatch`, which could not express these). Ignore files are discovered by walking **upward** from
  the scanned directory, so `graphify-sf force-app` still picks up the `.gitignore`/`.forceignore` at the
  project root. The existing `.graphifysfignore` is still applied, and the hardcoded `_SKIP_DIRS` floor
  (`.git`, `node_modules`, `.sfdx`, …) is unchanged.
- **`--include-ignored` flag** to opt out: scans every file regardless of `.gitignore`/`.forceignore` when
  you suspect a real metadata file was excluded.
- **Honest skip summary** printed after the scan, e.g.
  `skipped 57 files (.forceignore: 57) — use --include-ignored to include them`, so dropped files are
  never silent. (`detect()` now also returns `skipped_count`, `skipped_by_source`, and `respect_ignore`.)

### Fixed
- The post-scan log previously printed the raw `skipped` list object instead of a count
  (`… N skipped` now shows the actual number).
- **Distinct components with the same normalised label are no longer merged.** `deduplicate_by_label`
  collapsed any two nodes whose labels normalised the same — regardless of type — so an `ApexClass` and a
  similarly-named `LWCComponent`, or a `CustomObject` and its `CustomTab`/`Settings`/`PermissionSet`, were
  conflated into one node and their edges silently rewritten onto the wrong survivor. On a real 9k-node org
  this wrongly merged **83 node pairs**. Dedup is now gated on `sf_type`: only same-type nodes merge (the
  intended chunked-duplicate case still works), recovering those nodes and the object→field ownership edges
  that had been dropped (e.g. fields under a managed-package object whose label collided with a permission
  set).
- **Self-referencing lookup fields keep their `contains` ownership edge.** When a lookup/master-detail
  field points back at its own parent object, the object→field `contains` edge and the field→object
  `references` edge occupy the same undirected node-pair and one overwrote the other, leaving the field
  unattached to its object. The build now keeps the higher-priority relation on collision (`contains`
  outranks `references`), so `componentsOnObject`/`bfsImpact` see every field. Together with the dedup fix,
  object→field attachment on the test org went from 99.4% to **100%** (18 orphaned fields → 0). Preserving
  *both* relations on such pairs is the planned 0.4.0 MultiGraph work.

## [0.3.5] — 2026-06-13

### Fixed
- **Apex DML edges now work on real-world code.** The Apex DML → object `dml` edge feature added in
  0.3.4 silently produced **zero** edges on real Apex, because DML operands are almost always
  lowercase local variables (`insert c;`) and the edge-building guard only accepted operands whose
  name was already capitalized. Real classes with `insert`/`update`/`delete` statements therefore
  emitted no `dml` edges at all. The extractor now resolves the DML operand variable to its declared
  SObject type by scanning local variable declarations and method parameters (simple `Type var`,
  generic `List<Type>` / `Set<Type>` / `Map<K,Type>`, and parameters), and builds the `dml` edge to
  the resolved object (e.g. `Case c = new Case(); insert c;` → `class → object_case`,
  `operation="create"`, `confidence="INFERRED"`). Operands that cannot be resolved to a type are
  skipped rather than emitting a misleading edge to a variable name (honest INFERRED semantics
  preserved). Apex primitives (`String`, `Integer`, `Id`, etc.) are never treated as DML targets.
  A PascalCase operand that is itself a type name still works via a fallback path, so existing
  behavior is preserved.

  Note: in the built graph, multiple DML operations against the *same* object from one component are
  currently still merged into a single edge (the graph layer keeps one edge per source→target pair).
  Exposing every write operation as its own independently-locatable edge is planned as a follow-up
  graph-model upgrade.

## [0.3.4] — 2026-06-13

### Added
- **Apex DML edges now preserve the write operation.** Apex → object `dml` edges now carry
  an `operation` field derived from the DML verb (`insert`→`create`, `update`→`update`,
  `delete`→`delete`, plus the SF-native `upsert` / `merge` / `undelete` preserved as-is rather
  than forced into CRUD). The edge relation stays `dml` (unchanged) and confidence stays
  `INFERRED` — the DML target is a variable name that can't always be statically resolved to an
  object type, and that honesty label is unchanged. Deduplication is now by `(object, operation)`
  so a class that both inserts and updates the same object yields two distinct edges instead of
  one collapsed `dml` edge. This mirrors the flow record-op change in 0.3.3, so both major write
  paths (Flow and Apex) now expose read/write operation semantics to downstream consumers.
  SOQL `queries` edges are unchanged (they already carry read semantics).

## [0.3.3] — 2026-06-13

### Added
- **Flow record operations now preserve read/write semantics.** Flow → object edges from
  record operations (`recordLookups` / `recordCreates` / `recordUpdates` / `recordDeletes`)
  now carry an `operation` field (`read` / `create` / `update` / `delete`). The edge relation
  stays `references` (unchanged — that generic relation is reused by many extractors), so all
  existing consumers that filter by relation are unaffected; consumers that need to tell reads
  from writes can read the new field. Deduplication is now by `(object, operation)` instead of
  by object alone, so a flow that both reads and updates the same object yields two distinct
  edges instead of one collapsed reference. This lets downstream answer precise questions like
  "which flows *write* (update/create/delete) object X" rather than only "which flows touch X".

## [0.3.2] — 2026-06-12

### Added
- **npm distribution — install without Python.** `graphify-sf` is now installable from npm
  (`npm install graphify-sf` / `pnpm add graphify-sf`). A postinstall step downloads a
  self-contained, per-platform binary (built with PyInstaller) from the matching GitHub Release,
  so Node consumers can use the tool with no Python on the machine. Supported platforms:
  linux x64/arm64, macOS x64/arm64, Windows x64.
- **Programmatic JS API.** `require("graphify-sf").runGraphify(sfdxPath, { outDir })` spawns the
  binary (`<path> --out <outDir> --no-viz`) and resolves `{ code, graphJsonPath }`, so a Node
  daemon can drive the core static-extraction path directly. Also exports `ensureBinary()` and
  `binaryPath()`. The binary is downloaded lazily on first use when a package manager skips
  postinstall scripts (e.g. pnpm's default `ignore-scripts`), and any download failure throws
  a loud, explicit error rather than failing silently.
- **Release automation for binaries + npm.** The same `release: published` event now also builds
  the per-platform binaries (5-leg matrix), uploads them to the Release, and publishes the npm
  wrapper. The version is sourced from the release tag (single source of truth) — both the bundled
  binary and the npm package read it.

### Fixed
- **Frozen-binary version reporting.** The PyInstaller binary now reports its real version instead
  of `dev`, via a version-resolution fallback chain (`importlib.metadata` → bundled `_version.py`
  → `GRAPHIFY_SF_VERSION` env → `dev`). Source/PyPI installs are unaffected.
- **CI dependency scan no longer fails on transient `pip` advisories.** The security-scan job now
  upgrades `pip` in its environment before running `pip-audit`, so a freshly-published advisory
  against the bundled `pip` (which is not a project dependency) no longer reds every PR.

## [0.1.0] — 2026-05-12

### Added

#### Core pipeline
- Full offline SFDX metadata extraction — no org connection, no Salesforce CLI required
- Two-pass extraction: per-file structural pass + cross-file reference resolution
- `EXTRACTED` / `INFERRED` / `AMBIGUOUS` confidence tags on every edge
- Community detection via Louvain (default) and optional Leiden algorithm
- Plain-language `GRAPH_REPORT.md` with god nodes, surprising connections, and suggested questions
- Incremental updates (`--update`) with SHA-256 file hash manifest
- Dry-run diff with `check-update` (exits 1 if changes exist — CI-friendly)
- Parallel extraction with `--max-workers`

#### Supported metadata types
- `ApexClass`, `ApexTrigger`, `ApexMethod` — Apex source with SOQL, DML, callout, extends/implements extraction
- `Flow` — Flow/Process Builder with subflow, object, and field references
- `CustomObject`, `CustomField`, `ValidationRule`, `RecordType`, `Layout`
- `LWCBundle`, `AuraBundle` — component controller and child-component references
- `Profile`, `PermissionSet` — object/field/class permission edges
- `CustomLabel`, `NamedCredential`, `ExternalService`, `CustomMetadata`
- `Bot`, `BotVersion`, `GenAiPlugin`, `GenAiFunction`, `GenAiPlannerBundle`, `AiAuthoringBundle`, `PromptTemplate` — full Agentforce metadata graph

#### Export formats
- Interactive force-directed HTML (`graph.html`) with search, community filter, node inspector
- GraphRAG-ready JSON (`graph.json`) with node/edge provenance and community assignments
- D3 collapsible tree (`export tree`)
- Mermaid call-flow diagram (`export callflow-html`)
- Static SVG graph image (`export svg` — requires `[svg]` extra)
- Obsidian vault (`export obsidian`)
- GraphML for Gephi / yEd (`export graphml`)
- Neo4j Cypher statements + direct push (`export cypher` / `export neo4j`)
- Agent-crawlable Markdown wiki (`export wiki`)
- Graph merge (`merge-graphs`) with deduplication and re-clustering

#### Exploration CLI
- `query` — BFS/DFS traversal with token budget
- `explain` — full node details with `--relation` filter (no cap when filtered)
- `path` — shortest path between two metadata nodes
- `stats` — type distribution, edge relations, degree stats, density

#### LLM semantic extraction
- Six backends: Claude, Gemini, Kimi K2, OpenAI, AWS Bedrock, Ollama
- Auto-detect backend from available API keys (`--backend auto`)
- Adaptive retry with exponential back-off on rate-limit errors (429)
- Configurable token budget per chunk (`--token-budget`)

#### Integrations
- Agentic skill for Claude Code, Cursor, Codex, Kiro, Gemini CLI, aider, Copilot, and 10+ more IDEs
- `--link` flag for symlinked multi-IDE skill install
- AGENTS.md enforcement block (`agents install`) for always-on graph-first agent behavior
- CLAUDE.md block (`claude install`) for Claude Code
- Git post-commit + post-checkout hooks for automatic background rebuilds
- Git merge driver for conflict-free `graph.json` merges
- MCP stdio server with 8 tools and 6 resources
- File watcher with debounce and incremental rebuild
- `.graphifysfignore` for exclude patterns (gitignore syntax)
